# Search Design

## 目的

Wikipedia
RAGの検索アルゴリズムについて、現在の設計と、その設計になった理由を記録します。

## 基本的な考え方

初期構成は一般的なRAGでした。

``` text
質問
 ↓
Embedding
 ↓
FAISS
 ↓
上位チャンク
 ↓
LLM
```

しかしWikipediaでは、質問に含まれる記事タイトルの影響が強く、目的の記事自体は見つかっても、その記事内の目的箇所が上位に来ないことがありました。

例:

``` text
ロサンゼルス・ドジャースの大谷翔平について教えて
```

各チャンクに記事タイトルが含まれるため、同じ記事内の「球団史」「本拠地」などもEmbedding上で近くなり、「大谷翔平」に関するチャンクが埋もれる場合があります。

そこで検索を二段階に分けました。

``` text
質問
 ↓
どの記事か
 ↓
記事決定
 ↓
記事内のどこか
 ↓
LLM
```

この分離が現在の検索設計の中心です。

## SearchEngineの役割

``` text
SearchEngine
 ├─ 質問Embedding
 ├─ FAISS候補取得
 ├─ タイトル一致判定
 ├─ 記事内再検索
 ├─ lexical / title scoring
 ├─ float16 vectorによる再評価
 └─ Result生成
```

検索モードごとの利用方法は `SEARCH_MODES.md` を参照してください。

## article_focus

`article_focus`
は質問の先頭からWikipedia記事タイトルを特定し、特定できた場合はその記事だけを検索対象にします。

例:

``` text
質問:
ファイナルファンタジーXIVの漆黒のヴィランズについて教えて

記事:
ファイナルファンタジーXIV

記事内クエリ:
漆黒のヴィランズ
```

記事タイトル部分と依頼表現を除いた残差クエリを使い、記事内の全チャンクを再順位付けします。

記事を特定できなければ、広域検索へフォールバックします。

## タイトル一致の3段階判定

表記揺れを吸収しつつ、誤った記事へ固定しないため、タイトル一致は段階的に判定します。

### 1. 通常正規化一致

NFKC、大文字小文字、連続空白を正規化した完全一致です。

### 2. 英字・数字境界一致

英字と数字の境界にある空白だけを無視します。

``` text
Fallout 3 = fallout3
Windows 11 = Windows11
```

既存の `normalized_title` indexを利用します。

### 3. 一意なcompact一致

空白・中黒・ハイフン・句読点などを除去して比較します。

安全条件:

-   compact化後5文字以上
-   一致記事が1つだけ
-   候補取得は既存 `title_fts` で制限

一致が複数ある場合や候補を得られない場合は記事を確定せず、通常検索へフォールバックします。

確認例:

``` text
Fallout 3
fallout3
Ｆａｌｌｏｕｔ　３
```

これらが同じ記事へ入る一方、短い・曖昧なタイトルで誤った単一記事へ固定されないことを確認します。

## FAISSと再ランキング

production indexはチャンク単位です。

検索ではFAISSで候補を取得し、保存済みfloat16
vectorを利用できる場合は候補の類似度を再計算します。

FAISSは候補取得のための近似検索であり、Wikipedia固有の検索精度はタイトル特定や記事内検索を含む後段処理にも大きく依存します。

## lexical検索

Embeddingだけでは、固有名詞・作品内用語・節名などの文字列一致が十分に反映されない場合があります。

そのためタイトル一致、FTS、本文一致などのlexical情報を補助的に使用します。

記事が確定した後は、Wikipedia全体の意味的近傍を探すよりも、その記事内で質問の残差クエリに対応する箇所を見つけることを優先します。

## コンテキスト生成

検索結果は記事単位でまとめ、記事内順序を考慮してLLMへ渡します。

設計上の目的は、単に検索スコア上位の断片を大量に渡すことではなく、質問に必要な記事・必要な箇所へ絞ることです。

この変更により、検索精度だけでなくLLM入力文字数・入力トークン数・生成時間も削減できました。

## 改善するときの優先順位

検索品質を改善するときは、原則として次を先に検討します。

1.  タイトル抽出・一致判定
2.  記事内クエリ生成
3.  記事内FTS / lexical score
4.  前後チャンク展開
5.  記事内ランキング
6.  コンテキスト最適化
7.  必要ならRRF等の融合手法
8.  Embedding / FAISS構造

EmbeddingやFAISSは基礎検索として機能しているため、検索手順で改善できる問題に対してproduction
indexを再構築しないことを優先します。

## 評価方法

変更前後で同じ質問を使い、少なくとも次を比較します。

-   正しい記事が選ばれたか
-   欲しいチャンクが上位に来たか
-   関係ない記事へ固定されていないか
-   コンテキスト文字数
-   LLM入力トークン数
-   検索時間
-   応答時間

特にタイトル一致を緩める変更では、「ヒットする例」だけでなく、曖昧・短いタイトルで誤固定しないことも確認します。

## 維持したい原則

検索エンジンが、

``` text
どの記事か
記事内のどこか
```

までを決定します。

LLMは、

``` text
得られた資料をどう説明するか
```

を担当します。

この責務分離を維持することが、検索アルゴリズムを変更するときの基準です。
